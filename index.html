01How to read this

This guide is built to be used, not skimmed. Reading it end to end will feel productive and teach you almost nothing — that feeling is the illusion of fluency, and it's the main reason people grind two hundred problems and still freeze.

Three rules are baked into the page.

Predict before you peek. Every worked example is a pair: a slow version, then a fast one. When you hit the orange predict first marker, stop and answer in your head — better, out loud — before scrolling. Being wrong and then seeing the answer is worth several times more than reading the answer while nodding along. The struggle is the mechanism, not an obstacle to it.

Answers are hidden on purpose. The ▸ boxes are self-tests. Pulling something out of memory strengthens it far more than re-reading it does. Open the box only after you've committed to an answer, even a bad one.

Come back. One pass teaches nothing durable. Re-open the recall card in §14 tomorrow, in three days, in a week. Fifteen minutes of recall on day 7 beats two hours of fresh reading.

the honest version

Do the predictions and the self-tests and this page is maybe six hours of work spread over a few weeks, and most of it sticks. Read it straight through and it's forty minutes, and you'll retain about as much as from any article you read forty minutes ago.

02What DSA catches — and what it doesn't

The interesting question in 2026 isn't "is DSA still useful." It's which specific failures does this knowledge prevent, now that a model hands you working code in four seconds.

Both halves matter, because the pro-DSA case is usually oversold and that's exactly why it doesn't land.

DSA knowledge catches thisIt does not help with this
Code that works on your 50-row test and dies on 5 million. Nested loop, list membership test, pop(0) in a loop — invisible until scale. Whether the feature is the right feature. Product judgement is a different muscle entirely.
Code that solves a subtly different problem. The model optimised for looking correct; only you know the actual spec. Deployment, observability, on-call, the fifteen ways a distributed system fails. DSA is single-process reasoning.
Choosing the data structure before writing the loop. Most "clever algorithm" problems dissolve when the shape of the data is right. API design, naming, module boundaries — the things that decide whether a codebase is pleasant a year from now.
Reading a diff fast. Complexity is a compression format: "it's quadratic in the inner join" is one sentence instead of ten. Most business logic. A CRUD endpoint has no algorithmic content, and pretending otherwise is how people waste months.
Knowing when to stop optimising. Recognising that n is 200 and always will be is a DSA skill too. Making you a fast typist of boilerplate. That job is genuinely gone, and good riddance.

The shift is real: writing the algorithm got cheap, and judging it is now the expensive part. That's not a reason to skip DSA — you can't judge code in a domain you have no model of. But it changes what good practice looks like. Less "can I reproduce a heap from memory," more "can I look at 40 lines and see the quadratic."

A service takes a list of user IDs and, for each, finds their profile by scanning a list of 200,000 profiles. It's been fine for two years. What changed the day it wasn't fine, and what's the fix in one word?

Nothing changed about the code — n grew. A linear scan inside a loop is O(n·m); it was invisible at 30 IDs and became a timeout at 30,000. The one-word fix: hash. Build a {id: profile} dict once, look up in O(1).

This is the most common real-world performance bug there is, and it is Two Sum wearing a suit. You'll meet it again in §9.

03Cost intuition

Before any pattern, you need one number in your head:

the anchor

A typical machine does roughly 107 simple operations per second in Python (about 108–109 in C, Rust, or Java). Every runtime estimate below hangs off that one number. Memorise it and you can do the rest on your fingers.

Now the table that turns Big-O from an exam topic into a thing you feel. Each cell is wall-clock time at 107 ops/sec, using n²/2 for the quadratic column since most nested loops skip the pairs they've already seen.

nO(n) scanO(n log n) sortO(n²) nested loop
1,000instant1 ms50 ms — fine
10,0001 ms14 ms5 seconds — noticeable
100,00010 ms170 ms8 minutes — looks like a hang
1,000,000100 ms2 seconds14 hours
10,000,0001 second24 seconds58 days

Read the quadratic column again. The gap between "fine" and "your service is down" is one order of magnitude in n, and nothing in the code changes. This is why the bug always ships: it was correct and fast in every test you ran.

the flip side

At n = 1,000 the quadratic version takes 50 ms and the clever version takes 1 ms. Both are instant to a human. If n is bounded and small — a config list, a row of table columns, the sides of a polygon — the nested loop is the correct engineering answer, because it's shorter and more obviously right. Knowing this is part of the skill, not a betrayal of it.

Worked example: the shape of every optimisation

Two Sum. Given a list of numbers and a target, return the indices of two numbers that add to it. Here's the version everyone writes first, and it is not a bad first version:

version 1 — check every pair
def two_sum(nums, target):
    for i in range(len(nums)):
        for j in range(i+1, len(nums)):
            if nums[i] + nums[j] == target:
                return [i, j]
    return None                     # no pair exists

Correct. For n = 100 it does 4,950 pair checks and finishes before you blink.

predict first

At n = 100,000 this does about 5 billion checks. Using the anchor above — 107 ops per second — how long does it run? And before you scroll: what single fact is the inner loop re-deriving on every single pass?

version 2 — remember what you've seen
def two_sum(nums, target):
    seen = {}                       # value -> index
    for i, x in enumerate(nums):
        need = target - x
        if need in seen:            # O(1) lookup, not a re-scan
            return [seen[need], i]
        seen[x] = i
    return None

About 8 minutes → about 10 milliseconds. Same output, one pass, one dict.

The inner loop was asking "have I already seen the number that completes this pair?" — and answering it by re-reading the whole list, every time. The dict answers the same question in one step. That's the entire trick, and it is the same trick in a startling number of problems.

Version 2 is O(n) time. What did it cost, and when would you deliberately choose version 1 anyway?

O(n) extra space — the dict can hold every element. That's the trade at the heart of most speedups: you buy time with memory.

You'd choose version 1 when n is small and bounded (the constant-factor and allocation cost of a dict can genuinely lose at n = 20), when memory is the binding constraint rather than time, or when the values aren't hashable. "Which resource is scarce here?" is the question; O(n) time is only automatically better if memory is free.

Sorting a million-item list takes about 2 seconds by the table above. Your code sorts inside a loop that runs 500 times. Is that a problem? Show the arithmetic.

500 × 2 s = 1,000 seconds ≈ 17 minutes. Yes, that's a problem — and it's a sneaky one because each individual sort looks fast in a profiler.

The fix is almost always to sort once outside the loop, or to keep the data in a structure that stays ordered (a heap, a sorted container). Note the shape: the expensive thing wasn't wrong, it was in the wrong place. That's the "do it once" move from §4.

04The three moves

Patterns are easier to remember when you see what they're made of. Most of the speedups in this guide are one of three moves, and naming them gives you something to reach for when a pattern name won't come.

move 1 — remember

Spend memory so you never compute the same thing twice. A dict of what you've seen, a memo of solved subproblems, a prefix-sum array, a cache. Symptom that you need it: your inner loop is re-deriving a fact the outer loop already knew. Cost: O(n) or worse in space.

move 2 — order

Impose structure once, then exploit it many times. Sort, then two-pointer or binary search. Keep a heap so the extreme is always at hand. Use a tree so lookups are logarithmic. Symptom: you're repeatedly asking "what's the smallest / nearest / next larger." Cost: O(n log n) up front, or a log factor per operation.

move 3 — once

Arrange to touch each element a bounded number of times. Two pointers converging, a window sliding forward, a single scan carrying running state. Symptom: nested loops where the inner one never needs to go backwards. Cost: usually free — this is the move that buys speed without buying space.

and the ones that aren't

Three moves cover a lot, not everything. The honest remainder: divide and conquer (merge sort, quickselect — split, solve, combine), a better data structure (union-find, trie, segment tree — the structure is the algorithm), amortisation (an occasional expensive op paid for by many cheap ones, like dynamic array growth), closed form (a loop replaced by algebra), and randomisation / approximation (accept a good answer fast — sampling, HyperLogLog, Bloom filters). If a problem resists all three moves, it's usually one of these.

Stacks and queues are worth a separate note: they don't speed anything up by themselves. They're structural — they let you express "process this later, in this order" so that a scan becomes possible at all. When you see a stack in a solution, look for which of the three moves it's enabling.

Classify each: (a) prefix sums, (b) binary search on a sorted array, (c) merging two sorted lists, (d) counting distinct items with a set.

(a) Remember — precompute cumulative totals so any range sum is one subtraction.
(b) Order — the sortedness is the whole leverage; without it, binary search is meaningless.
(c) Once — two pointers walking forward, each element visited exactly one time.
(d) Remember — memory in exchange for never re-scanning to ask "have I seen this?"

If you said "order" for (c), that's defensible too: the input being sorted is the precondition. Both moves are present. Classification isn't the point — noticing why it's fast is.

"Should I learn min-max?"

This deserves a direct answer because the phrase means two different things and only one of them matters to you.

yes — running min/max

Carrying the smallest or largest value seen so far as you scan. This is essential, it's in the table above, and it shows up constantly. Practise it until it's reflex: best answer so far plus best ingredient so far, updated in one pass. Kadane's algorithm (§6⑤) is exactly this idea applied to sums.

no — minimax (the game-tree one)

Minimax with alpha-beta pruning is the algorithm behind chess engines and tic-tac-toe bots: you alternate between a player maximising the score and one minimising it, searching a tree of moves. It's genuinely interesting, but it is niche. It essentially never appears in interviews outside game-AI roles, and it won't help you review a backend diff. Skip it for now; build it as a weekend project later if games interest you.

Two more things worth knowing about the primitives, because both cause real bugs:

Python's sort is stable and adaptive. Stable means equal elements keep their original relative order, which lets you sort by multiple keys in passes (sort by secondary key, then by primary). Adaptive means Timsort exploits runs that are already ordered — sorting an already-sorted list is O(n), not O(n log n). Both facts occasionally turn an ugly problem into an easy one.

A heap is not a sorted list. Printing heap gives you an array in heap order, which looks scrambled. Only heap[0] is meaningful. To get the k smallest you pop k times (O(k log n)), and to get everything sorted you may as well have used sorted().

You need the 10 largest items out of a 10-million-item stream that doesn't fit in memory. Which tool, and what's the cost?

A min-heap of size 10. Push each item; when the heap exceeds 10, pop the smallest. At the end the heap holds the top 10.

Time O(n log k) — with k = 10 that log is about 3.3, so it's effectively a linear scan. Space O(k) = 10 items, which is the actual point: sorting would need all 10 million resident. This is the canonical case where a heap beats a sort, and it's worth noticing why: you never needed the full order, only the boundary.

06The eight patterns

Eight recurring shapes. Between them they cover the large majority of array, string, and graph problems you'll meet in interviews and a good chunk of what you'll meet at work.

what's deliberately not here

Eight is not all of them. Not covered below: intervals (merge, overlap — sort by start, then one pass), backtracking (permutations, N-queens, sudoku), union-find, tries, linked-list manipulation (reversal, cycle detection), shortest paths with weights (Dijkstra, Bellman-Ford), and bit manipulation. Pick these up after the eight are solid; the eight are the ones with the best return per hour, not a complete map.

Every pattern below gives you its invariant — the thing that stays true on every iteration. If you remember nothing else about a pattern, remember its invariant. It's what lets you write the code from scratch instead of recalling a template, and it's what you say out loud in an interview to show you actually understand it.

① Hashing & counting remember

invariant The map always holds the complete answer for everything I've already walked past — so I never need to look backwards.

Fires when you catch yourself asking "have I seen this before," "how many of each," "does a matching partner exist," or "group these by something."

The mechanic is always the same: one pass, and at each element you either query the map about the past or record the present into it. Order matters — Two Sum queries before it records, which is what stops an element from pairing with itself.

The counting variant deserves its own reflex. collections.Counter turns "are these anagrams," "which character appears most," "is there a duplicate within k positions" into two or three lines. Grouping is the same idea with defaultdict(list): compute a key for each item, append it under that key. Anagram grouping is just key = tuple(sorted(word)).

Gotcha: hash lookup is O(1) on average, not always — see §8. And the key must be hashable: a list can't be a dict key, a tuple can.

  • easyTwo Sum · Contains Duplicate · Valid Anagram
  • medGroup Anagrams · Top K Frequent Elements · Longest Consecutive Sequence
  • hardSubarray Sum Equals K (hashing + prefix sums — the crossover problem)
Longest Consecutive Sequence: given an unsorted array, find the longest run of consecutive integers. Sorting gives O(n log n). How does a set give you O(n) — and why isn't the obvious set solution accidentally quadratic?

Put everything in a set. Then for each value x, only start counting if x-1 is not in the set — meaning x is the beginning of a run. Walk up from there while x+1, x+2, … are present.

The guard is the whole trick. Without it you'd walk the full run from every member of the run, which is quadratic on input like [1..n]. With it, each run is walked exactly once from its start, so the total inner work across the entire loop is O(n).

Notice the shape: the outer loop looks like it might be expensive, and you have to reason about total work rather than per-iteration work to see that it isn't. That style of argument — amortised counting — comes up again in two pointers and monotonic stacks.

② Two pointers once

invariant Everything outside the two pointers has already been decided and will never need revisiting. Each pointer only moves in one direction, so total work is O(n).

Fires when the array is sorted (or you can sort it), and you're looking for a pair, a triple, a partition, or a palindrome check. Also when you're comparing two sequences that both advance forward.

Why converging pointers are correct is worth internalising, because it's the part people can't explain in interviews. On a sorted array with lo at the left and hi at the right: if a[lo] + a[hi] is too small, then a[lo] paired with anything at or below hi is also too small — because everything below hi is smaller. So lo can be discarded entirely, not just this one pair. Each move eliminates a whole row or column of the pair space. That's the argument, and it's why the sortedness is load-bearing.

The fast/slow variant uses two pointers at different speeds in the same direction: cycle detection in a linked list (Floyd's), finding the middle in one pass, removing the nth node from the end. Different mechanic, same discipline.

Gotcha: deduplication in 3Sum. After fixing an element you must skip over equal neighbours or you'll emit the same triple repeatedly. Roughly half of failed 3Sum attempts are correct algorithms with a duplicate-handling bug.

  • easyValid Palindrome · Merge Sorted Array · Remove Duplicates from Sorted Array
  • med3Sum · Container With Most Water · Sort Colors (Dutch national flag — three pointers)
  • hardTrapping Rain Water (then solve it again with a monotonic stack — see ⑤)
Container With Most Water: two vertical lines form a container; area is min(height[lo], height[hi]) × (hi - lo). Start wide and move inward — but which pointer do you move, and what's the proof you can't miss the answer?

Move the pointer at the shorter line.

Proof: the area is capped by the shorter line. If you moved the taller one inward, the width strictly decreases and the height is still capped by that same shorter line — so every container you could reach that way is no better than the one you already measured. Therefore no optimal solution is lost by discarding the shorter line entirely.

That last sentence is the shape of every two-pointer correctness argument: "the pointer I move can be eliminated because no better answer involves it." If you can say that sentence about a problem, two pointers applies.

③ Sliding window once

invariant The window [L, R] always satisfies the constraint after the shrink step, and the running state (sum, counts, distinct-count) always describes exactly that window.

Fires when you want the longest, shortest, or best contiguous run satisfying some condition. Contiguity is the tell — if the problem lets you pick non-adjacent elements, this is not your pattern.

The shape is always: expand R by one and update state; while the constraint is violated, shrink from L and undo state; then record the answer. Both pointers only move right, so it's a single pass even though it reads like a nested loop.

def longest_unique(s):
    seen = {}                        # char -> last index seen
    L = best = 0
    for R, ch in enumerate(s):
        if ch in seen and seen[ch] >= L:
            L = seen[ch] + 1         # jump L past the earlier copy
        seen[ch] = R
        best = max(best, R - L + 1)
    return best
the precondition nobody states

Sliding window is only correct when shrinking the window can actually fix a violation — that is, when the constraint is monotone in window size. "Sum ≤ k with all-positive numbers" is monotone: drop an element and the sum can only fall. Introduce a negative number and it isn't.

Try the standard "longest subarray with sum ≤ 0" window on [1, -2, 1]. It reports 2. The true answer is 3 — the whole array sums to exactly 0. The window shrank away from index 0 to fix a violation, and never came back, so it could never see the full array.

This is the most dangerous kind of bug in the guide: it doesn't crash, it doesn't warn, it just quietly returns a slightly wrong number on inputs your tests don't cover. Whenever you reach for a window, ask "can the input go negative — or more generally, can removing an element make things worse?" If yes, you need prefix sums plus a hash map (or a monotonic deque), not a window.

  • easyMaximum Average Subarray I (fixed-size window — start here)
  • medLongest Substring Without Repeating Characters · Longest Repeating Character Replacement · Permutation in String
  • hardMinimum Window Substring (the boss fight — a variable window with a compound condition)
In Minimum Window Substring you track how many required characters are still missing. Why is a single integer counter enough — why don't you have to re-compare the whole frequency map on every step?

Because you can maintain the counter incrementally, which is the real skill in every window problem. Keep need = a Counter of the target, and missing = the number of required characters not yet satisfied. When you add a character, decrement its need; only if the need for that character was still positive does missing drop by one. Reverse it on shrink.

Re-comparing the whole map would be O(alphabet) per step and would give you back a factor you paid to remove. The general rule: window state must be updatable in O(1) on both add and remove. If it can't be, sliding window is the wrong tool — that's the same precondition as the box above, in a different costume.

④ Binary search order

invariant The answer is always inside [lo, hi]. Every iteration halves that range without ever excluding the answer.

Fires when the search space is monotone: there's a point where "no" flips to "yes" and never flips back. A sorted array is the obvious case. The non-obvious case is more valuable.

Binary search on the answer

This is the technique worth real study, and most people meet it as a magic trick instead of a method. The setup: you can't compute the answer directly, but given a candidate answer you can cheaply check whether it works — and if a candidate works, every larger candidate also works. That's monotonicity, and it means you can binary search the answer space itself.

Worked example. A conveyor belt must ship packages of given weights, in order, within D days. What's the minimum ship capacity?

def min_capacity(weights, D):
    def days_needed(cap):            # the cheap "does this work?" check
        days, load = 1, 0
        for w in weights:
            if load + w > cap:
                days += 1; load = 0  # start a new day
            load += w
        return days

    lo = max(weights)                # must fit the heaviest single package
    hi = sum(weights)                # one giant day always works
    while lo < hi:
        mid = lo + (hi - lo) // 2
        if days_needed(mid) <= D:
            hi = mid                 # feasible — try smaller, keep mid as candidate
        else:
            lo = mid + 1             # infeasible — mid is definitively out
    return lo

The whole method in three questions: What am I searching over? (capacities from max to sum.) What's my feasibility check? (simulate the days — O(n).) Is it monotone? (A bigger ship never needs more days.) Answer those three and the code writes itself. Total cost O(n log(sum)).

Once you see it, you see it everywhere: minimum eating speed, splitting an array into k subarrays minimising the largest sum, the smallest divisor under a threshold, "can we do it in time T." All the same three questions.

template discipline

Off-by-one errors in binary search are so common that the fix is procedural, not clever: pick one template and always use it. The one above — while lo < hi, hi = mid on success, lo = mid + 1 on failure, return lo — finds the leftmost value satisfying a predicate and never infinite-loops, because mid always rounds down and lo strictly increases in the else branch.

Also: write mid = lo + (hi - lo) // 2, not (lo + hi) // 2. In Python integers are arbitrary-precision so it makes no difference — but this exact overflow bug lived in the JDK's own binary search for nearly a decade, and in any fixed-width language it's real. Build the habit where it's free.

And in real Python, use bisect.bisect_left / bisect_right for plain sorted arrays. Hand-rolling is for interviews and for the on-the-answer variant.

  • easyBinary Search · First Bad Version · Search Insert Position
  • medSearch in Rotated Sorted Array · Find Peak Element · Koko Eating Bananas (on-the-answer)
  • hardSplit Array Largest Sum · Median of Two Sorted Arrays
Find Peak Element: in an array where no two neighbours are equal, find any index bigger than both its neighbours. The array isn't sorted. Why is binary search still valid?

Because a peak is guaranteed to exist in the half you keep. Look at mid: if a[mid] < a[mid+1], then the right half starts on an upward slope, and a slope must eventually either turn over (a peak) or run into the boundary (also a peak, since edges count). So a peak must exist to the right — discard the left half. Symmetrically otherwise.

The lesson generalises: binary search doesn't need sortedness. It needs a rule that lets you throw away half the space while proving the answer survives in the other half. Sortedness is just the most familiar source of such a rule.

⑤ Stacks & the monotonic stack structural

invariant Plain stack: the top is always the most recent thing still waiting to be resolved. Monotonic stack: the stack is always sorted (increasing or decreasing), so anything it evicts has just found its answer.

Fires when you need to match things in nested order (brackets, tags, expression parsing), undo the most recent action, or — the one worth learning properly — answer "for each element, what's the next bigger/smaller one to its right?"

The monotonic stack, actually explained

Problem: for every element, find the next element to its right that's larger. The obvious solution scans right from each position: O(n²).

The insight is to invert the question. Instead of each element hunting for its successor, each new element announces itself to everyone still waiting. Keep a stack of indices whose answer isn't known yet, maintained in decreasing value order. When a new value arrives, everything on the stack smaller than it has just found its next-greater — pop them and record it.

def next_greater(nums):
    res = [-1] * len(nums)
    stack = []                       # indices, values decreasing bottom -> top
    for i, x in enumerate(nums):
        while stack and nums[stack[-1]] < x:
            res[stack.pop()] = x     # x is the answer for that waiting index
        stack.append(i)              # i now waits for its own answer
    return res                       # anything still on the stack has no next greater

Why it's O(n) despite the inner while: each index is pushed exactly once and popped at most once. The inner loop can run many times on one iteration, but across the whole run it executes at most n times total. That's an amortised argument — the same style you met in Longest Consecutive Sequence — and being able to say it out loud is a genuine signal of understanding.

The monotonic direction encodes what you're asking. Decreasing stack → next greater element. Increasing stack → next smaller. Same eight lines, one comparison flipped.

Gotcha: decide up front whether ties count. < versus <= in that while loop is the difference between "next greater" and "next greater or equal," and it silently changes answers on inputs with duplicates.

  • easyValid Parentheses · Min Stack · Baseball Game
  • medDaily Temperatures · Next Greater Element II · Evaluate Reverse Polish Notation · Asteroid Collision
  • hardLargest Rectangle in Histogram · Trapping Rain Water (you've already solved this with two pointers — do it again this way and compare)
Daily Temperatures asks: for each day, how many days until a warmer one? You have next_greater above. What's the one change — and what does the stack hold at the very end on input [73,74,75,71,69,72,76,73]?

Store the distance instead of the value: res[j] = i - j where j = stack.pop(). Everything else is identical.

At the end the stack holds indices 6 and 7 (values 76 and 73). 76 is the array's maximum and 73 is the last day; neither ever finds a warmer one, so both answers stay 0.

The pops per step are [0, 1, 1, 0, 0, 2, 2, 0]. Notice that 72 at index 5 and 76 at index 6 each clear two waiting days in a single iteration while five of the eight iterations pop nothing at all. That lumpiness is the amortisation happening in front of you: no single step is bounded, but the total across all steps is.

⑥ Trees & graphs — BFS and DFS structural

invariant BFS: the queue only ever holds nodes at distance d and d+1 from the start, so the first time you reach a node is via a shortest path. DFS: the call stack is always exactly the current root-to-node path.

Fires when data is connected — a hierarchy, a network, a grid, a dependency list, a state space where moves lead to more states. Note that grids are graphs: each cell is a node with up to four neighbours, and half of "matrix" problems are BFS wearing a costume.

Choosing between them: if the question is "shortest," "fewest steps," or "minimum moves" on an unweighted graph, use BFS — that's not a preference, it's the only one of the two that's correct. If the question is "does a path exist," "explore everything," "what's the deepest," or anything naturally recursive, DFS is simpler.

# BFS — shortest path in an unweighted graph
from collections import deque

def bfs(start, graph):
    dist = {start: 0}                # doubles as the visited set
    q = deque([start])
    while q:
        node = q.popleft()
        for nxt in graph[node]:
            if nxt not in dist:      # mark WHEN ENQUEUED, not when dequeued
                dist[nxt] = dist[node] + 1
                q.append(nxt)
    return dist                      # shortest distance to every reachable node

Using the distance map as the visited set is a small idiom worth stealing — one structure, no way for the two to disagree.

three bugs that get everyone

1. Marking visited at dequeue instead of enqueue. If you mark when you pop, the same node can be queued many times before it's ever popped, and a wide graph turns exponential. Mark it the moment you push it.

2. Forgetting visited entirely on a cyclic graph. Trees have no cycles so you get away with it; general graphs loop forever. Grid problems are cyclic — you can always walk back where you came from.

3. Recursive DFS on deep input. CPython's recursion limit is about 1,000 frames. A path-shaped graph of 10,000 nodes raises RecursionError. Convert to an explicit stack rather than raising the limit — see §8, where raising it is worse than it sounds.

Topological sort, and detecting cycles while you're there

"Order these so every dependency comes before the thing that needs it." Build order, course prerequisites, task scheduling, spreadsheet recalculation. The DFS version gives you cycle detection free if you use three colours rather than a boolean:

  • White — not visited yet.
  • Grey — currently on the recursion stack; we're inside its subtree right now.
  • Black — fully finished, all descendants explored.

Reaching a grey node means you've looped back into your own ancestry: that's a cycle, and the ordering is impossible. Reaching a black node is fine — it's an already-finished branch, just skip it. A single boolean can't tell those two cases apart, which is why the naive version reports cycles on perfectly valid diamond-shaped dependency graphs. Append each node to the output as it turns black, then reverse at the end.

(The BFS alternative, Kahn's algorithm, repeatedly removes nodes with in-degree zero. If the output is shorter than the node count, there's a cycle. Same information, different shape — learn one properly first.)

Rotting Oranges: a grid where rotten oranges infect adjacent fresh ones each minute. Find the minute everything is rotten. Why does starting BFS from one rotten orange at a time give the wrong answer?

Because rot spreads from all rotten oranges simultaneously. One-at-a-time BFS measures each source's distance independently, so a fresh orange gets timestamped by whichever source you happened to run first, rather than by the nearest one.

The fix is multi-source BFS: seed the queue with every rotten orange before the loop starts, all at distance 0. The BFS invariant does the rest — the first time a cell is reached is still the shortest path, now measured to the nearest source. It costs one extra line and it's a genuinely reusable trick (nearest exit, walls and gates, distance-to-nearest-anything).

Don't forget the final check: if any fresh orange remains unreached, return −1.

⑦ Heaps order

invariant Every parent is ≤ (or ≥) its children, so the extreme element is always at the root. Nothing else is ordered, and nothing else needs to be.

Fires when you repeatedly need the current smallest or largest from a collection that keeps changing. Top-k, k-th anything, merging sorted streams, scheduling by earliest deadline, "process the cheapest option next" (which is what Dijkstra's algorithm is).

The k-sized heap trick is the one to have at your fingertips: to keep the k largest items, maintain a min-heap of size k. The smallest of your winners sits at the root, so each new item is one comparison away from being accepted or rejected. O(n log k) time, O(k) space — and unlike sorting, it works on a stream you can't hold in memory. (Inverted for k smallest: use a max-heap. Python only has a min-heap, so push -x or a tuple with a negated key.)

Two heaps, for a running median

Worth teaching properly because it's the classic "I've heard of it but couldn't write it" problem. Keep the lower half of the numbers in a max-heap and the upper half in a min-heap. Then the two candidate medians are always sitting at the two roots.

The whole algorithm is two rules, applied on every insertion:

  1. Push, then transfer. Add the new number to the max-heap (low side), then immediately move its largest element over to the min-heap. This guarantees the ordering property — everything in low ≤ everything in high — without any comparisons or special cases.
  2. Rebalance. If the min-heap is now larger than the max-heap, move its smallest back. Sizes stay within one of each other.

Read the median: if sizes differ, it's the root of the bigger heap; if they're equal, it's the average of the two roots. Insert is O(log n), median is O(1). The push-then-transfer ordering is what removes all the case analysis — most buggy implementations try to decide which heap to push to first.

Gotcha: heaps don't support "remove an arbitrary element" cheaply. If your problem needs that (a sliding-window median, say), you need lazy deletion — keep a dict of pending removals and discard stale roots as they surface — or a different structure entirely.

  • medK Closest Points to Origin · Task Scheduler · Reorganize String · Kth Largest Element in an Array
  • hardFind Median from Data Stream · Merge k Sorted Lists
Merge k sorted lists with n items total. Compare: (a) concatenate and sort, (b) merge two at a time, (c) a heap of size k. Which wins, and when might the "worse" one be right?

(a) O(n log n) — throws away the sortedness you were handed.
(b) Naively merging list 1 into 2 into 3… re-walks the accumulated result each time: O(nk). Pairwise/tournament merging fixes this to O(n log k).
(c) Heap holding one candidate per list, pop the smallest and push that list's next: O(n log k) time, O(k) space.

(c) is the answer, and its real advantage isn't the time bound — it's that it works on streams, holding only k items at once. If the lists are files too big for RAM, (a) isn't even available.

When is (a) right? When n is small, or when the lists are short and numerous and you value four lines you'll never have to debug over an asymptotic win nobody will measure. Say that out loud in an interview — it reads as judgement, not laziness.

⑧ Dynamic programming remember

invariant Every subproblem is solved at most once, and its answer never changes afterwards. The table is a permanent record of settled facts.

Fires when the problem asks for the number of ways, the best possible value, or whether something is achievable — and a natural recursive definition exists where the same subproblem shows up in more than one branch. That overlap is the entire justification for DP. If subproblems never repeat, memoising buys you nothing and you just have recursion.

Step 1 — write the honest recursion

Climbing Stairs. You can take 1 or 2 steps at a time; how many distinct ways to reach step n? To arrive at step n you were either at n−1 or n−2, so:

version 1 — correct, and unusable
def climb(n):
    if n <= 2: return n
    return climb(n-1) + climb(n-2)

Beautifully direct. Also the reason this section exists.

predict first

Before scrolling: for n = 40, roughly how many function calls does that make? Order of magnitude is fine — thousands? millions? billions? And how many distinct subproblems are there really?

the actual numbers, measured

For n = 40, climb makes 204,668,309 calls to compute a result of 165,580,141. Along the way it re-enters climb(10) 1,346,269 separate times — recomputing the identical answer over a million times.

At roughly 107 operations per second that's about 20 seconds of CPU for a value you could write down in a table of forty entries. Push to n = 50 and it's 25 billion calls — about 40 minutes. At n = 53 you're past three hours. Each step of n multiplies the work by 1.6.

version 2 — one line of memory
from functools import cache

@cache                               # that's it. that's the fix.
def climb(n):
    if n <= 2: return n
    return climb(n-1) + climb(n-2)

204 million calls → 40 executions of the function body, one per distinct value of n. From exponential to linear, with a decorator.

do not write it this way

You'll see this hand-rolled version everywhere, including in a previous draft of this very guide:

def climb(n, memo={}):               # ← the bug is on this line
    ...

A mutable default argument in Python is created once, at function definition time, and shared by every call forever. Here it happens to be harmless because the cache is valid for all inputs — but change the function to take a second parameter (climb(n, max_step)) and the memo silently serves answers computed for a different problem. It's the same class of bug as a global cache with no key, and it is genuinely one of the most common Python footguns in existence.

Use @cache. If you must hand-roll: def climb(n, memo=None): then if memo is None: memo = {}.

Step 2 — turn the recursion inside out (tabulation)

Memoisation is top-down: start at the answer, recurse down, cache on the way back up. Tabulation is bottom-up: fill the small cases first and build forward. Same recurrence, no recursion:

def climb(n):
    if n <= 2: return n
    dp = [0] * (n + 1)
    dp[1], dp[2] = 1, 2
    for i in range(3, n + 1):
        dp[i] = dp[i-1] + dp[i-2]
    return dp[n]

Tabulation is usually a little faster (no call overhead) and — the part that matters in production — it has no recursion-depth ceiling. The memoised version still recurses n deep on the first call, so climb(5000) raises RecursionError while the loop version doesn't care. See §8.

Step 3 — notice you only need two cells

def climb(n):
    a, b = 1, 2                      # ways to reach step 1, step 2
    for _ in range(3, n + 1):
        a, b = b, a + b
    return b if n > 1 else a

O(n) time, O(1) space. The general rule: if the recurrence only reaches back a fixed number of rows, you can throw the rest of the table away and keep a rolling window. This works on 2-D DP too — many grid problems collapse from an m×n table to a single row.

The 2-D case: reading a DP table

Longest Common Subsequence, "ABCD" vs "ACBD". dp[i][j] = LCS length of the first i characters of one and first j of the other.

Kadane's algorithm, and the problem it is not

Maximum Subarray: find the contiguous run with the largest sum. Kadane's is DP with a two-variable table:

def max_subarray(nums):
    cur = best = nums[0]
    for x in nums[1:]:
        cur = max(x, cur + x)        # extend the run, or start fresh here
        best = max(best, cur)        # best run ending anywhere so far
    return best

The DP state is "best subarray ending exactly at i," and the recurrence is that one max. On [-2,1,-3,4,-1,2,1,-5,4] it returns 6. Two variables instead of an array is just the O(1)-space collapse from Step 3.

a distinction worth keeping straight

Best Time to Buy and Sell Stock looks like Kadane's cousin, and it is frequently — including in the previous version of this guide — filed under sliding window. It is neither. There's no window that grows and shrinks; it's a single scan carrying a running minimum:

def max_profit(prices):
    lowest = prices[0]; best = 0
    for p in prices[1:]:
        best = max(best, p - lowest)
        lowest = min(lowest, p)
    return best

Two variables, one pass, no window. Filing it under the wrong pattern isn't a trivia error — it teaches you to reach for a shrinking window on problems where shrinking means nothing, which is exactly how people end up writing a correct-looking window with a wrong answer.

  • medCoin Change · Longest Increasing Subsequence · Unique Paths · Word Break · Maximum Subarray
  • hardEdit Distance · Longest Common Subsequence · 0/1 Knapsack
Coin Change with coins [1, 3, 4] and target 6. Greedy (take the biggest coin that fits, repeatedly) gives what? What's optimal? What does the gap tell you about when greedy is allowed?

Greedy takes 4, then 1, then 1 → 3 coins. Optimal is 3 + 3 → 2 coins. Greedy is wrong, on an input this small.

The lesson: greedy only works when a locally best choice provably cannot rule out the global optimum, and that has to be argued, not assumed. It happens to hold for US/Euro coin systems, which is exactly why the intuition feels safe and why the bug ships. Change the denominations and it collapses.

Practical rule: when you're tempted by greedy, spend sixty seconds hunting a counterexample. If you find one, you need DP. If you can't find one, try to state why in one sentence ("sorting by end time is safe because…"). If you can neither break it nor justify it, use DP — it's O(n·k) and it's provably right.

The constraints are a hint channel people ignore. n ≤ 20 means exponential is expected. n ≤ 2,000 means O(n²) passes and you probably shouldn't burn interview time on the linear solution. n ≤ 10⁵ means you need O(n log n) at worst. n ≤ 10⁹ means you're not allowed to touch every element at all — think binary search on the answer, or a closed-form.

Self-test — name the pattern for each, then check. (1) Find the length of the longest substring containing at most two distinct characters. (2) Given a list of meeting intervals, can one person attend all of them? (3) Find the smallest positive integer missing from an unsorted array, in O(n) time and O(1) extra space.

(1) Sliding window ③. Contiguous, longest, and the constraint ("at most two distinct") is monotone in window size — shrinking can only reduce the distinct count, so shrinking always fixes a violation. Textbook fit.

(2) Sort, then one pass ②-ish. Sort by start time, then check whether any meeting begins before the previous one ended. This is the intervals family — not one of the eight, which is why the §6 box warns you the eight aren't exhaustive. If you said "hash map," notice that nothing here asks "have I seen this."

(3) A trap. The O(1)-space constraint rules out the hash set you instinctively reached for. The trick is to use the array itself as the hash table — place each value v in the range 1…n at index v−1 by swapping, then scan for the first index that doesn't hold its own value. This is a genuinely hard problem, and the point of including it is that the constraints are part of the problem statement. "O(1) space" changes which patterns are even legal, and most people read past it.

08Gotchas that actually bite

These are the things that turn a correct algorithm into a production incident. Every one has cost someone a bad evening. The numbers below are measured on CPython 3.11, not estimated.

Recursion has a hard ceiling, and raising it is worse than it looks

CPython's default recursion limit is 1,000 frames. A recursive DFS on a graph shaped like a chain — a linked list, a path, a degenerate tree, a 100×100 grid that's one long corridor — hits RecursionError well before the data is large by any normal standard.

The instinct is sys.setrecursionlimit(100000). Don't. That limit exists to stop you overflowing the C stack, which Python cannot detect. Raise it far enough and instead of a clean exception you get a segmentation fault: the process dies instantly, no traceback, no logs, nothing to debug. A crash you can catch has been traded for one you can't.

The real fixes, in order of preference: rewrite as an explicit stack (mechanical — push what you'd have recursed into), or use bottom-up tabulation for DP, which has no depth ceiling at all. This is a concrete reason to know both DP forms rather than just the pretty one.

# recursive DFS -> iterative, mechanically
def dfs(start, graph):
    seen, stack = {start}, [start]
    while stack:
        node = stack.pop()
        for nxt in graph[node]:
            if nxt not in seen:
                seen.add(nxt)
                stack.append(nxt)

Hash lookup is O(1) on average

Three caveats that the "O(1)" shorthand hides. Worst case is O(n) — with enough colliding keys, a dict degrades to a linked list, and adversarially chosen keys have been used as a real denial-of-service attack (this is why Python randomises string hashes per process). Hashing isn't free — it's O(k) in the size of the key, so hashing million-character strings is not a constant-time operation no matter what the table says. Growth costs — dicts resize and rehash everything, so an individual insert can be expensive even though the average across inserts is fine.

And the everyday one: keys must be hashable. A list can't be a key, a tuple can. d[[1,2]] raises TypeError; d[(1,2)] is fine. In practice this decides how you encode grid coordinates and memo keys.

What unites these: the expensive operation is invisible at the call site. Nothing about x in items announces that it's a linear scan. This is exactly the class of bug generated code is full of, because it reads beautifully.

Space is a budget too

Almost everyone reports time complexity and forgets space, then gets an out-of-memory kill in production. Some anchors worth carrying: a Python int is ~28 bytes, a list of a million ints is roughly 40 MB once you count pointers, and a dict is ~2–3× the raw data size. So "just memoise it" on a problem with 10⁸ distinct subproblems is not a solution — it's an OOM with extra steps.

The BFS-versus-DFS diagram in §6 is the clearest case: same problem, same time bound, wildly different memory profile. On a wide graph BFS can hold a huge frontier; on a deep one DFS blows the stack. Choosing between them is a space decision.

Greedy needs a proof, not a vibe

Covered in the §6⑧ self-test, and worth repeating because it's the most confident kind of wrong: coins [1,3,4], target 6. Greedy gives 3 coins, optimal is 2. If you can't state in one sentence why the locally best choice is globally safe, don't use greedy.

Sorting surprises

Python's sort is stable (equal elements keep their input order — so you can sort by secondary key first, then primary), and adaptive (already-sorted input is O(n), not O(n log n)). Both can be exploited. Meanwhile sorted([1, "a"]) raises TypeError in Python 3, and sorting a list of dicts or custom objects needs an explicit key= — sorted(objs) won't guess.

Code review: this function is meant to find duplicates in a list of 500,000 order IDs. Name every problem you can see.def dupes(ids): out = [] for i in ids: if ids.count(i) > 1 and i not in out: out.append(i) return out

1. ids.count(i) scans the entire list — inside a loop over the entire list. That's 500,000 × 500,000 = 2.5×1011 operations. At 107 ops/sec that's roughly seven hours. On the developer's 100-item test file it finished instantly.

2. i not in out is a second linear scan — cheaper because out is small, but it's the same mistake again and it would dominate if most IDs were duplicated.

3. Order of results depends on input order, which may or may not be intended but is undocumented either way.

The rewrite is O(n) time, O(n) space, and shorter:

from collections import Counter
def dupes(ids):
    return [x for x, n in Counter(ids).items() if n > 1]

This is the single most useful review reflex to build: a linear operation inside a loop is quadratic. count, index, in on a list, remove, a nested query, a slice — all of them look like one cheap step and none of them are.

09Three production case studies

The complaint that DSA is interview theatre usually comes from people who've never seen the patterns wearing work clothes. Here are three, with the arithmetic.

Case 1 — the N+1 query is Two Sum

An order-history endpoint. The ORM makes it look innocent:

orders = Order.objects.filter(user=user)[:200]
for o in orders:
    print(o.customer.name)           # ← one SELECT per order, silently

Each attribute access is a database round trip. 200 orders means 201 queries. At a very ordinary 2 ms per round trip that's 400 ms of pure latency on an endpoint that should take 5 ms — and it multiplies by every concurrent user, so the database connection pool saturates long before anyone notices the page is slow.

The fix, in ORM terms, is select_related or prefetch_related. But look at what those actually do: fetch all the customers in one query, build a dict keyed by id, and look each one up in O(1). That is Two Sum. Identical structure — a repeated expensive lookup replaced by one pass plus a hash map. The remember move, applied to network calls instead of array elements.

Why the pattern knowledge matters here: you can memorise "use select_related" as a Django incantation, or you can recognise the shape and then catch the same bug in a REST client loop, a Redis loop, an S3 loop, or a microservice fan-out — none of which have an ORM to rescue you.

Case 2 — the rate limiter is a sliding window

"Allow 100 requests per user per minute." The naive implementation resets a counter each minute — which lets a user send 100 requests at 11:59:59 and 100 more at 12:00:01, doubling the intended rate at the boundary.

The correct version is literally the pattern from §6③: keep a deque of timestamps per user, drop everything older than 60 seconds from the left, and check the length.

from collections import deque
window = deque()                     # timestamps, oldest at the left

def allow(now, limit=100, span=60):
    while window and window[0] <= now - span:
        window.popleft()             # shrink: evict what left the window
    if len(window) >= limit:
        return False
    window.append(now)               # expand
    return True

Expand on the right, shrink from the left, maintain state in O(1) — the same three lines you wrote for Longest Substring Without Repeating Characters. And the same amortised argument applies: the while looks nested, but every timestamp is appended once and popped once.

The engineering caveat is real, though: at a million users this stores a million deques. Production systems trade exactness for memory here — a fixed-window counter with two buckets, or a token bucket, which approximates the same behaviour in O(1) space per user. Knowing the exact algorithm is what lets you evaluate the approximation instead of cargo-culting it.

Case 3 — an incident, minute by minute

A composite of a very common shape. Read it as a story about review, not about algorithms.

timeline

Tuesday, 14:20. A ticket asks for a report of customers who appear in both the billing export and the CRM export. An engineer asks a model for it, gets thirty lines back, tests it on the sample files (800 rows each — 640,000 comparisons, about a twentieth of a second), gets the right answer instantly, and ships it. The code does for b in billing: for c in crm: if b.email == c.email. It's correct.

Tuesday, 14:35. Review. Two approvals in nine minutes. The code is clean, well named, and has a passing test — one that the same model wrote, using the same 800-row fixture, and which therefore validates the exact same misunderstanding of scale.

Thursday, 02:10. The nightly job runs against production: 240,000 billing rows and 310,000 CRM rows. That's 7.4×1010 comparisons — roughly two hours of CPU at 107 ops/sec, versus the twentieth of a second the sample took. The input grew 300×; the runtime grew 100,000×.

Thursday, 04:30. The job is still running. It holds a database transaction open, so the connection pool is exhausted; the morning batch queues behind it. Nothing has crashed — every dashboard is green, because from the outside it just looks slow.

Thursday, 09:15. Someone notices the reports are missing. The fix takes four minutes: build a set of CRM emails, scan billing once. Runtime drops to under a second.

Nobody in this story was incompetent, and the AI wasn't wrong — it answered the question it was asked. The failure is that no one in the chain looked at thirty lines of code and thought "what is n here?" That question takes four seconds and it is the entire skill. It's also, notably, not something the model volunteers unless you ask.

What single review comment would have prevented this, and what test would have caught it?

Comment: "This is O(n·m). What are the real row counts in production?" That's it. It doesn't require reading the logic carefully or knowing the domain — just noticing a loop inside a loop over two collections whose size isn't visibly bounded.

Test: one that runs against realistic volume, or at minimum a scale-sanity assertion — generate 50,000 synthetic rows and assert the function completes in under a second. AI-generated tests almost never do this, because they're written to demonstrate correctness on the example, and correctness on the example is precisely what was never in doubt.

That's why "does it have tests?" is a weaker review question in 2026 than it used to be. The tests exist. They test the wrong thing, confidently.

10Reviewing the code AI hands you

This is where the practice pays rent daily. Five checks, in the order that catches the most for the least effort. Under a minute for a typical function.

  1. What is n, and what happens when it's 100× bigger? Find the loops. Are any nested? Is there a linear operation hiding inside one — in on a list, .count(), .index(), a slice, a database query, an HTTP call? Then ask what the real-world size of n is and what it will be in two years. This one check catches most of what actually breaks.
  2. How much memory does it hold at peak? Does it build a list of everything before processing any of it? Read a whole file into a string? Memoise an unbounded key space? Time complexity is what people report; memory is what gets the process killed. Watch particularly for caches with no eviction policy — they're invisible until they aren't.
  3. What are the edge cases, and does it handle them or just avoid crashing on them? Empty input, one element, all elements identical, already sorted, reverse sorted, negative numbers, zero, duplicates, unicode in a string problem. Negatives deserve special suspicion around anything window-shaped (§6③) — that's a silent wrong answer, not an exception.
  4. Did it solve the problem I actually have? The most dangerous failure mode, because the code is clean and confident and does something reasonable — just not your thing. Re-read your requirement, then re-read the code, and check them against each other rather than against your memory of what you asked for.
  5. Do the tests test anything? If the model wrote both the implementation and the tests, they share a single author's understanding — including its mistakes. Tests that pass on a 10-row fixture prove nothing about the 10-million-row case. Add one adversarial input yourself: empty, huge, or malformed.
the meta-check

Ask the model directly: "What's the time and space complexity of this? What input would make it slow? What did you assume about the data that I didn't tell you?" It usually answers accurately — models are better at analysing code than at remembering to analyse it unprompted. But you need enough of a model of your own to know whether the answer it gives you is true. That's the whole argument for learning this material in one sentence.

  • "Explain the invariant of this loop in one sentence, then ask me a question that checks whether I understood it."
not these
  • "Solve this." — You'll read a correct solution, feel it click, and be unable to reproduce it on Thursday. This is the illusion of fluency, delivered on demand.
  • "Is this right?" before you've traced it yourself on a small input by hand.
  • "Explain sliding window" as your first move on a new pattern. Struggle for ten minutes first — the explanation lands on prepared ground and sticks several times better.

The one that changes results most is the quiz-me prompt. Pattern recognition is the bottleneck skill, and it's the one you can't build by reading solutions. Ten unlabelled prompts, name the pattern, no code — that's a five-minute drill you can do on a phone, and it maps directly onto the thing an interview actually tests.

12A six-week plan

About five hours a week: an hour on four weekdays, a longer session at the weekend. Roughly 45 problems total, which is far fewer than the internet will tell you to do and enough if you do them properly.

the rule that makes it work

From day 6 onward, start every session with one problem from a previous week, unlabelled. Don't look at which pattern it belongs to. This is interleaving, and it's the difference between building recall and building recognition-in-context.

Blocked practice — twenty window problems in a row — feels dramatically better. You get fast, you feel fluent. It also means you never once had to decide what to use, which is the only decision the interview asks you to make. Interleaved practice feels worse and measures better, consistently, across decades of studies. Trust the discomfort.

what "done" means

Not "I solved it." A problem is finished when you can, without looking: (a) state the invariant in one sentence, (b) write the solution in about fifteen minutes, (c) give its time and space complexity, and (d) name one input that would break the naive approach.

If you can't do (d), you learned a template, not a pattern.

13The interview itself

Interviews still ask these questions, and the format has shifted in a specific way worth preparing for: many companies now let you use an AI assistant and then interrogate you about the result. That's a different exam. It rewards judgement over recall, which is good news if you've been practising the way this guide suggests.

Three things carry most of the weight.

Talk about the input before the algorithm. "How big can this get? Can the values be negative? Are there duplicates? Is it already sorted?" This isn't stalling — it's the single clearest signal that you've worked on real systems, and it frequently changes the correct answer. It also buys you thinking time that reads as diligence rather than silence.

Say the brute force out loud, then improve it. "The obvious approach is check every pair, which is O(n²) — for n up to 10⁵ that's about eight minutes, so I need better. The inner loop is re-scanning to ask whether a complement exists, and a hash map answers that in one step." That narration is the interview. Jumping straight to the optimal solution from memory demonstrates less, not more, because the interviewer can't see any reasoning to evaluate.

State the complexity of what you wrote — both kinds — and one input that would hurt it. Volunteering the weakness of your own solution is the most senior-sounding thing you can do, and almost nobody does it.

if AI is allowed in the room

Then the interview isn't about producing the code; it's about your review of it. Use the §10 checks out loud. "It generated this — my concern is ids.count() inside the loop, which makes it quadratic. Let me check the constraints… n is 10⁵, so that's too slow. I'll ask it to use a Counter." That transcript is worth far more than silently producing the same final code, because it shows the thing they're actually hiring for: that you can be the judgement layer over a very fast, very confident, occasionally wrong collaborator.

14One-page recall card

Everything above, compressed. Don't read it — cover the answers and try to produce them. Come back tomorrow, in three days, in a week. Fifteen minutes of this beats an hour of re-reading, and it isn't close.

The anchor

~107 simple operations per second in Python. n=10⁵ with a nested loop ≈ 8 minutes. n=10⁶ ≈ 14 hours.

The three moves

Remember — spend memory, never compute the same thing twice (hash map, memo, prefix sums).
Order — impose structure once, exploit it many times (sort, binary search, heap).
Once — touch each element a bounded number of times (two pointers, sliding window, running state).
Not everything fits: divide & conquer, a better data structure, amortisation, closed form, randomisation.

The eight invariants — say them from memory

① HashingThe map holds the complete answer for everything already passed.
② Two pointersEverything outside the pointers is decided; each pointer moves one way only.
③ WindowThe window satisfies the constraint after shrinking, and the state describes exactly it.
④ Binary searchThe answer is always inside [lo, hi]; each step halves it without losing the answer.
⑤ Mono stackThe stack stays sorted; whatever it evicts has just found its answer.
⑥ BFS / DFSBFS: queue holds only distance d and d+1 → first arrival is shortest. DFS: the stack is the current path.
⑦ HeapParent beats children, so the extreme is at the root. Nothing else is ordered.
⑧ DPEach subproblem is solved once and never changes.

The five preconditions that cause silent wrong answers

  • Sliding window needs shrinking to be able to fix a violation. Negatives break it. [1,-2,1], sum ≤ 0 → says 2, truth 3.
  • Two pointers needs sortedness (or another reason the discarded side can't hold the answer).
  • Binary search needs monotonicity, not sortedness.
  • Greedy needs a proof. Coins [1,3,4], target 6 → greedy 3, optimal 2.
  • Memoisation needs subproblems that actually repeat, and a key space small enough to fit in memory.

The Python landmines

  • Recursion limit ~1,000 frames. Don't raise it — segfault, not exception. Use an explicit stack or bottom-up DP.
  • x in list is O(n). Inside a loop it's quadratic. Build a set. (2,000× measured.)
  • pop(0) is O(n) — use deque.popleft(). (180× measured.)
  • s += ch in a loop is quadratic — build a list, then "".join(). (100× measured.)
  • Slicing copies. arr[mid:] in a recursion destroys the log.
  • def f(x, memo={}) — the default is created once and shared forever. Use @cache.
  • Hash O(1) is average, keys must be hashable, hashing itself is O(key length).

The review question

"What is n here, and what's inside the loop?"

Four seconds. Catches most of what actually breaks in production.
